Outpatient Front Desk

A scheduling assistant that registers patients, issues queue tickets and reserves a compatible room and doctor, without ever giving either one to two patients at once.

  • Python and Tkinter
  • SQLite, on this computer only
  • No internet, no extra packages

assignment.pyassign_patient()

First fit: the first free room and the first free doctor

  1. Check the caseDated today, not already holding a pair, not marked done.
  2. List what is freeRooms in that ward that are in service and unreserved; doctors who serve that ward and are unreserved.
  3. Reserve both, or neitherNothing changes until a room and a doctor both exist. Reserving the room first could leave it stuck with no doctor.

assignment.pyapp.py

Three ways to assign, one set of rules

Assign selected

Takes the first compatible free room and doctor, in the order they are configured.

Fast and predictable for the usual case.

Choose room/doctor...

Opens a chooser listing only the rooms and doctors actually free for that ward.

Staff may know which room has the right equipment. They can change which pair is used, never whether it is allowed.

Auto-assign all

Serves every waiting case dated today, first come, first served.

A blocked case waits with its reason and the run continues, so one full ward never holds up another. Pairs already given are never reshuffled.

All three call check_case_is_assignable() and available_resources(), so they can never disagree about who is eligible or what is free.

storage.pyclinic.db

The queue survives a restart

CREATE TABLE IF NOT EXISTS registrations (
    row_id              INTEGER PRIMARY KEY,
    appointment_date    TEXT NOT NULL,
    queue_id            TEXT NOT NULL,
    patient_name        TEXT NOT NULL,
    medical_information TEXT NOT NULL,
    phone_number        TEXT NOT NULL,
    destination_ward    TEXT NOT NULL,
    ward_code           TEXT NOT NULL,
    status              TEXT NOT NULL DEFAULT 'waiting',
    completed_at        TEXT,
    UNIQUE (appointment_date, queue_id)
);
  • Date plus ticket is unique.The database itself refuses a duplicate, even if the code had a bug.
  • row_id keeps arrival order.The queue reloads in the order people registered.
  • Reservations are not saved; status is.A reservation means "right now". Restored tomorrow, it would hold a room for a visit that already happened.
  • Older files are upgraded.migrate() adds new columns to an existing clinic.db instead of asking anyone to delete it.
  • The file stays on this computer.It is excluded from git and never sent anywhere.

ExampleRow 4 has a date that does not exist, so the whole file is refused and none of the three patients is saved.

  • Check everything, then writeEach row is validated exactly like a typed registration before anything is saved, then all rows go in one transaction.
  • Report every problem at onceProblems are listed by the row number the spreadsheet shows, with the header as row 1, so the file is fixed in one pass.
  • Tickets are always generatedA file cannot supply its own queue ID, so imported cases follow the same ticket rule as everyone else.

Three worth knowing

  • The arrival-order test registers tickets in descending order, so code that sorted by ticket number would fail.
  • A database in the old shape, with a patient in it, is upgraded and the patient is still there afterwards.
  • Every test uses a temporary database, so running them never touches the saved queue.

Honest limits, and what comes next

Not true yet

  • Reservations mean "now": no time slots, shifts or calendar
  • No urgency field; the queue runs in arrival order
  • First fit is predictable, not the best possible pairing
  • No lasting patient identity, so one person registered twice is not spotted
  • Nothing detects that a visit ended; staff press Mark done
  • One computer; two open windows don't share a queue until restart
